# Code patches for XC2 3.0.1 main (recomp/patches.py).

# xc2fps (XC2_FPS60, on): the frame rate of the frame limit XC2_FPS_LIMIT (frame_rate.c). XC2 paces its frames as
# XCX 2.0.0 does (recomp/patches-upd.txt, set xcx60): a frame interval in vsyncs at main+0xb75c40, set to 2 at boot; a
# vsync period, a virtual of the graphics device that returns 1/60 s (main+0x6bdc50); a frame-time getter that returns
# interval * period (main+0x6a36bc), the step the game takes; and a limiter (main+0x6aafd8) that spins until the time
# since the frame started passes interval * period * 0.997. Found in 3.0.1 by profiling the main thread (XC2_PROFILE);
# masagrator's Xenoblade2DynFPS (2.1.0, GPL-2.0, read for behaviour only) sets the same interval from the present
# interval and scales the game's step.
set xc2fps XC2_FPS60 1
# The boot setter's interval (main+0x6e3f44 calls main+0x6a4078 with 2): 1 vsync per frame; frame_rate.c sets 2 again
# in cutscenes.
site xc2fps main 6e3f44 321f03e0 320003e0
# The vsync period: the patch page's +0x40 (1 / limit, or the measured frame time in play), so interval * period, the
# game's step, follows the frames.
site xc2fps main 6bdc54 bd459500 @page:x8 bd404100
# The limiter's wait, interval * period * 0.997 against the time since the frame started: the page's +0x48, the frame
# time of the limit. x8 is dead here: the loop calls main+0x6e26f8 next, or returns.
site xc2fps main 6ab168 1e2a0800 @page:x8 bd404900
# The grass and wind sway step (main+0x748658: s6 = 1/30, the step it moves per frame): the page's +0x50, the step the
# game takes this frame (frame_rate.c xc2_steps_store). x8 is the constant's page here and unused after.
site xc2fps main 74865c bd414906 @page:x8 bd405106
# Right-stick camera turn: the player camera's update (around main+0x1d1240) adds the stick, after its smoothing, times
# the yaw speed (+0x52dc) and the pitch speed (+0x52e0) of its speed table (camera.param's YawRotSpeed and
# PitchRotSpeed per camera speed option, filled at main+0x1cdda8) to the yaw (+0xb8) and the pitch (+0xc0) each frame,
# with no frame time, so above 30 fps the camera turned faster. Both speeds are scaled where they are loaded by the
# page's +0x54, the step this frame times 30 (frame_rate.c xc2_steps_store), as XCX's turn (patches-upd.txt, xc260).
# x8 is rewritten before it is read again at both (a call, then an adrp); s1 is free at both.
site xc2fps main 1d12c8 bc696900 bc696900 @page:x8 bd405501 1e210800
site xc2fps main 1d1314 bc696900 bc696900 @page:x8 bd405501 1e210800

# xc2res (XC2_OUTPUT_RES, resolution.c): the size the game composes its frame in. XC2 composes 1280x720 (docked and
# handheld): two getters of its graphics device return 1280 (main+0x6e3fc8) and 720 (main+0x6e3fd0), and the window
# setup (main+0x700640) sizes the window textures with the same constants. All three read the patch page's +0x70
# (width) and +0x74 (height) instead.
set xc2res XC2_OUTPUT_RES 0
site xc2res main 6e3fc8 5280a000 @page:x0 b9407000
site xc2res main 6e3fd0 52805a00 @page:x0 b9407400
site xc2res main 700640 5280a015 @page:x21 b94072b5
site xc2res main 700644 52805a16 @page:x22 b94076d6
# The graphics heaps (main+0x6f4ee4 fills their sizes, main+0x705c20 carves GLIBCNT, GLIBPXL, GLIBVTX, ... from one
# block of their sum): the render targets come from GLIBPXL, 0x16a00000 bytes (362 MiB), the high half of x9 here;
# above 1280x720 the game aborts in its allocator (main+0x6e927c). The size is the page's +0x78 instead
# (resolution.c xc2_res_init); the movk that follows sets the low half, GLIBCNT, as before.
site xc2res main 6f4f74 d2e2d409 @page:x9 b9407929 d3607d29
# The game's memory layout (main+0x6421b4, handed to main+0x6e3f34): the main heap, then a 512 MiB graphics block
# (orr w8, wzr, #0x20000000) that GLIB's heaps are carved from. Its size is the page's +0x7c instead (the same growth).
site xc2res main 6421c4 320303e8 @page:x8 b9407d08

# Markers on the 3D scene (target cursor, damage numbers, talk and quest icons) are placed in the interface's

# screen-to-world (main+0x6c3c84) and game code read. The camera update (main+0x6c2b90) copies the viewport from the
# render surface's size (main+0x6d76f0, the frame size); its three loads of that size read the page's +0x80/+0x84
# instead (1280, 720), so the markers follow the 1280x720 the game was made for. The aspect it derives (+0x1f0) is the
# same at any 16:9 size, and the renderer takes its viewport from the render targets, so the scene keeps the frame
# size. x9 and x10 are the loaded values themselves. Game code (below main+0x600000) that asks the graphics device for
